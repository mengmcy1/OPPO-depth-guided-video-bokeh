## 稳定问题背景

课题原文面向云端离线精修，以 OPPO 手机双目系统记录的高帧率 RGB 视频与低帧率粗糙深度为输入，目标是研究深度补全、主体及边界处理、可控虚化和时序一致性的统一视频虚化方法。

原文已提出共享时序表征、深度/alpha/虚化三个输出分支、物理渲染与神经残差结合的候选路线，并提出数据集（数据制作方案）、训练模型与代码等交付目标。原文计划为 2026 年 10—12 月完成数据准备与 baseline 搭建，2027 年 1—5 月优化方法与中期检查，2027 年 6—9 月提升效果和效率并结题。这些是提案内容，具体实现、可行性、时间安排和最终验收口径仍需确认。

材料来源：`00_项目资料/OPPO影像课题提报模板_给学生.pdf`，研究计划部分。Windows 端此前仅检查本地 clone；当前 Linux 服务器的实际挂载与环境已另行核实，见下文。各机器路径与环境不能互相套用。

### 阶段 E1：准备最小 Synthetic 数据素材

第一轮只构建 **5 个 scene × 25 帧**，不直接生成 200 个完整测试视频。

固定：

```text
Resolution = 1024 × 576
Frames = 25
Scenes = 5
Foreground source = VideoMatte240K / AM-2k
Background source = BG-20K
Focus target = 1 / scene
Blur strength K = 先固定一个中等值，暂定 K=16
Random seed = 固定
```

每个 scene 首先只生成公共输入，不生成最终 GT：

```text
scene_xxxx/
├── rgb/
├── disparity/
├── depth/          # 若当前几何能稳定转换则保存
├── alpha/
├── mask/
└── metadata.json
```

`metadata.json` 至少记录：

- foreground / background 来源；
- random seed；
- object 数量、位置和前后关系；
- per-frame geometry；
- focus target / focus value；
- K；
- resolution；
- frame count。

验收标准：

1. 5 个 scene 均能稳定生成 25 帧；
2. RGB、Alpha、Mask、Disparity 时间对应关系正确；
3. 前后景遮挡关系正确；
4. 不存在明显越界、空 Mask 或损坏帧；
5. 固定 seed 后可重复生成同一场景。

### 阶段 E4：K 与 Blender 光圈控制标定

Any-to-Bokeh 使用参数 (K) 表示虚化强度，Blender 使用相机光圈等物理参数。

第一轮不要直接猜固定映射。

构建一个简单标定场景：

```text

固定 foreground depth
固定 background depth
固定 focus distance
只改变 Blender aperture
```

1. 先核对代码中 K、深度/视差的单位和归一化方式，明确焦点距离、物体深度、焦距、传感器尺寸及图像分辨率如何进入虚化尺度关系，再确定一套统一公式或统一标定规则。

| 合成方式 | 全图 MAE | 全图 PSNR/dB | soft MAE | soft MSE | soft PSNR/dB |
|---|---:|---:|---:|---:|---:|
| sRGB | 0.001139 | 50.0815 | 0.011383 | 0.0004392 | 36.5350 |
| 线性 RGB 后转回 sRGB | 0.001626 | 43.7488 | 0.036262 | 0.0032498 | 26.7662 |

60/60 张的 soft MAE 均为 sRGB 更低。结论仅为：**官方估计 FG/BG 与保存原图的重合成一致性更符合 sRGB 口径**。不能从中推断真实拍摄的物理混合空间，也不能据此认定 sRGB 恢复器更准确；残差包含估计误差与 JPEG 编码等影响。此检查不改变 Cycles 的线性光照流程。

数值评价另需注意：在线性空间、不额外裁剪的相同 Alpha/背景重合成中，差值为 Alpha×(F_est−F_ref)，与新背景无关。黑/白/棋盘等背景用于边缘视觉诊断，不可充当多份独立数值证据；转为 sRGB 后的显示域误差会受背景影响，若后续使用必须声明评价空间。

#### E7 VideoMatte 动态源策略（待冻结）

Any-to-Bokeh 官方公开 `dataset_synthsis.py` 的 test-generation 路径启用了 `BG_test`、`merge_f25_test.json` 和 `gen_test_flag=True`；同一文件给出的 `merge_f25_test.json` 格式示例包含 `AM-2k/train` 与 `VideoMatte240K_JPEG_HD/train` 路径，同时保留了一个被注释的 VideoMatte official test clip 清单路径。由于真正的 `merge_f25_test.json` 没有公开，不能据此确认论文最终 200-video test set 的具体 source split，也不能证明其 source-level train/test 隔离。

因此 E7 当前记录以下两层方案，**尚未视为正式 scene freeze**：

- **Strict Held-out Dynamic Subset**：主测试动态部分优先使用 VideoMatte240K official `test` 的 5 个独立源视频。允许从同一 source 生成多个 25-frame clip、背景和 Focus/Depth/`K` 条件，但全部保留同一个 `source_video_id`，不把派生 clip 当作新的独立动态源；统计时保留 per-source grouping，必要时先 source 内聚合再对 5 个 source 求均值。
- **Dynamic Extended Stress Set（可选）**：若 5 个 source 的动作/发丝/衣物/遮挡覆盖不足，可额外选取 E1–E6 未使用的 VideoMatte `train` source 做动态压力测试，但必须与严格 held-out 主结果分开报告；Any-to-Bokeh 的公开生成代码存在使用 VideoMatte `train` source 的痕迹，因此不能保证其预训练阶段未见过这些源。

如果后续确实需要更多独立 held-out 动态源，优先评估另一个具有明确 test split 且提供前景/Alpha 的 video matting 数据集，而不是把大量 VideoMatte train source 直接并入主 held-out 表。正式冻结时需记录主/扩展子集、原始 source ID、scene-level 与 source-level 统计口径。
