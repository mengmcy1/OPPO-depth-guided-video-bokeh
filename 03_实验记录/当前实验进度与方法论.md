## 1. 研究主线

本项目当前面向云端离线精修的视频虚化研究，**不再把低帧率粗深度补全预设为必须实现的核心创新**。现阶段以公开方法复现为基础，重点分析 Any-to-Bokeh 的计算/显存成本与可重复失败场景，再据此确定 Ours 的针对性改进。

当前研究逻辑改为：

> **扩充并冻结 baseline → profile Any-to-Bokeh 时间/显存瓶颈 → 系统定位特定失败场景 → 用证据确定 Ours → 做最小可验证改进。**

**MagicBokeh已完成Synthetic与同配置成本评价**，补充了单步扩散、Real-ISR和RGB内部估深范式的参照。当前保留模型计算成本和视频端到端效率两种性能评价；新服务器两种成本评价及Any-to-Bokeh原生模块归因均已完成，效率优化和失败分析暂不开展。

课题原文中的低帧率双目粗深度、Token Merging、Depth/Alpha/Bokeh 多头与物理渲染残差仍作为历史提案和候选思路保留，但当前不再作为 Ours 的强制前置。若后续 failure analysis 或导师要求重新指向低帧率输入问题，再恢复专项实验。

本轮结论只推进到以下四点：

1. **时间**：VAE编码及重叠＋时序解码合计占80.36%；7.8411秒的重叠/解码组最耗时，不能把整组耗时全部归给decoder。原8次插桩Core=20.1707秒，正式Core仍20.1128秒。
2. **峰值**：RGB/CoC编码达到≈34.29GiB allocated；history在全部6个编码阶段的requested高区间验证5×4.5GiB并发分配及22.5GiB请求增量，入口/出口状态不能取代这个存活证据，也没有形成完整allocated resident分解。
3. **缓存、临时分配、预留池**：RGB旧完整缓存与新一级cache在高区间共存；CoC保留当前RGB cache而不创建它。native同步状态的inactive_split在预热结束/clip结束为2.837935/2.944510GiB，reserved为41.691406GiB，这些不是峰值瞬间碎片构成。参数存储及原生FP32 upcast已单列；非PyTorch CUDA内存仍未解释，不承诺清理预留进入32GiB。
4. **一个单因素实验（待验证，未实施）**：新证据优先支持只检查VAE encoder ResNet返回处`output_scale_factor=1`时是否可省去除法，保留原加法及decoder/UNet/batch/precision/cache/窗口/采样。冻结checkpoint在CPU仅做metadata检查，10个encoder残差模块scale均为1。先以相同种子流程检查随机状态、采样形状/次数、缓存顺序和25帧逐值/RGB8差异，再独立测RGB/CoC及完整运行峰值与未插桩Core；随后按需验证另3固定片段。降显存、加速、输出等价和32GiB目标均待验证。原16→8编码微批量只保留为先前候选，本轮未实施。

## 4. 结果讨论

### 已有结果说明了什么

- **输入与适配方式对结果有实质影响。** Dr.Bokeh 在同 200 段上的输入对照中，GT Alpha 相对 Full-public 的 PSNR 在 198/200 段改善。该证据支持分割输入及其引起的后续分层、修复与补全过程是差异的重要来源；已知图层分支同时改变多个因素，应按整体输入条件解释。见[输入效应分析](records/drbokeh-input-effect-analysis-20260929.json)。
- **当前已恢复可比较的结果，但论文性能版图尚未完全恢复。** MPIB、BokehMe、BokehDiff 的候选选择及 DeepLens 结果均已记录依据，部分绝对分数和方法排序仍与论文不同。现阶段成果是声明条件下的公开代理复现；当前 200 段参与过配置选择，属于复现开发证据。详见统一协议中的 Table 1 / Table V。
- **控制能力和视觉问题需要结合数值理解。** DeepLens 单级路径在 K16/32 上全部达到 aperture 上限，虚化不足及部分亮度、边缘偏差仍可观察到；BokehDiff 的复核保留了弱虚化不足、强虚化过度平滑和细节重绘等现象。它们说明现有方法在控制响应与视觉保真之间仍有值得分析的问题，尚不能据此归纳所有方法的统一失效原因。见[DeepLens 复核](records/deeplens-track-a-final-review-20260929.json)与[BokehDiff 复核](records/bokehdiff-final-review-20260929.json)。

### 对后续研究的启发

**基于现有证据的判断**：当前最值得投入的是 Any-to-Bokeh 的效率与失败机制，而不是先画一个新网络。已有 Table 3A 显示其模型级采样峰值显存约38.47GiB，且已有 Synthetic/DAVIS结果可用于筛选失败场景；首轮模块profile已定位VAE为主要成本，下一步验证机制并开展case analysis。

**待下一阶段回答的问题**：高分辨率FP32编码activation与6.47GiB缓存分别能降低多少成本？重叠窗口的重复编码哪些能在保持随机流及解码语义的前提下复用？哪些ATB质量问题能在多个场景稳定复现？这些仍是待验证的问题，不能将profile直接写成改进收益。
